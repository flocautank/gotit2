Les langages de la data, situés

SQL, Python, R, DAX, Spark… On les cite en rafale comme s’ils étaient concurrents. Ils ne le sont presque jamais : chacun intervient à un endroit précis de la chaîne.

Intermédiaire7 min3 animations

Une donnée suit toujours le même parcours : elle est collectée, stockée, transformée, analysée, puis restituée à quelqu’un. Situer un langage, c’est simplement dire à quelle étape il travaille.

Scène 1 — Qui travaille où

Le parcours est toujours le même.Collecter, stocker, transformer, analyser, restituer. Un projet data, c’est cette chaîne — rien de plus.

SQL règne au milieu.C’est le langage pour parler aux bases : sélectionner, filtrer, regrouper, croiser des tables. Si vous ne devez en connaître qu’un, c’est celui-là.

Python prend le relais quand ça se complique.Appeler un service, nettoyer du texte, entraîner un modèle, automatiser toute la chaîne : tout ce qui dépasse une requête.

DAX vit dans les tableaux de bord.C’est le langage de Power BI : il calcule des indicateurs au moment où l’on clique sur un filtre.

Spark, lui, est une question de taille.Ce n’est pas vraiment un langage mais un moteur : il répartit le calcul sur des dizaines de machines quand une seule ne suffit plus.

SQL, en une image

Scène 2 — Une requête est une phrase

On part d’une question en français.C’est toujours ainsi que ça commence — et c’est la partie difficile.

SELECT : ce que je veux voir.Les colonnes à afficher, et les calculs à faire dessus — ici, une somme.

FROM … JOIN : où je vais le chercher.Les tables concernées, et comment elles se rejoignent. C’est le lien par identifiant vu dans la leçon précédente.

WHERE : ce que je garde.Le filtre. Voilà, vous savez lire une requête SQL : trois lignes qui disent quoi, où, et à quelle condition.

SQL ou Python ? La bonne question

Scène 3 — Deux outils, deux gestes

SQL dit ce qu’on veut, pas comment le faire.On décrit le résultat attendu, la base se débrouille. Et elle travaille là où les données sont déjà : c’est pour ça qu’elle est imbattable sur les gros volumes.

Python dit comment faire.Étape par étape. On y va dès qu’il faut une logique que SQL ne sait pas exprimer : du texte à nettoyer, un modèle à entraîner, un service à interroger.

La bonne pratique tient en une phrase.Réduire d’abord avec SQL — passer d’un milliard de lignes à dix mille — puis travailler en Python. L’inverse consiste à ramener un entrepôt entier sur un ordinateur portable.

Le reste du vocabulaire, une ligne chacun

Les langages

  • SQL — interroger une base. Le socle.
  • Python — le couteau suisse : nettoyage, automatisation, IA.
  • R — le cousin statisticien de Python, très présent en recherche et en santé.
  • DAX — les calculs à l’intérieur de Power BI.
  • Scala / Java — les langages historiques des très gros volumes.

Les outils qu’on cite avec

  • Spark — un moteur qui répartit le calcul sur plusieurs machines.
  • pandas — la boîte à outils Python pour manipuler des tableaux.
  • dbt — organise et documente les transformations SQL.
  • Power BI / Tableau — la restitution : tableaux de bord.
  • No-code — les mêmes gestes à la souris, sans écrire de code.

Les formats

  • CSV — un tableau en texte brut. Universel, fragile.
  • JSON — une fiche avec des champs libres, imbriqués.
  • Parquet — un format compressé, rangé par colonnes, fait pour l’analyse.
  • API — pas un format : une porte pour venir chercher la donnée.
Pour situer quelqu’un en réunion

« Je fais du SQL » → il interroge des bases, souvent côté analyse ou BI. « Je fais du Python » → il transforme, automatise, ou fait du modèle. « Je fais du Spark » → il travaille sur de très gros volumes. « Je fais du Power BI » → il restitue, c’est lui que verront les décideurs.

À retenir

  • Les langages de la data ne sont pas concurrents : ils occupent des étapes différentes.
  • SQL interroge les bases — c’est le socle, et il se lit comme une phrase.
  • Python prend le relais dès que la logique dépasse une requête.
  • DAX vit dans les tableaux de bord, Spark répond à un problème de volume.
  • La règle d’or : filtrer au plus près des données, travailler ensuite.
